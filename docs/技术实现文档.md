## 1. 目标与约束

**要解决的问题**:纯向量 RAG 在多跳推理、关系型查询、跨文档聚合三类 query 上系统性失效;同时企业级交付要求多租户隔离、人机协同、评估闭环、全链路可观测。

**硬约束**(违反即视为未交付):
- 四道租户隔离防线缺一不可(存储/身份/查询/验收)。
- 图谱、精排、交叉验证必须可开关;非核心环节故障不得阻断主流程。
- 切片、图谱写入、异步任务三处必须幂等。
- 中断状态与服务重启后可恢复。

**非目标**:模型预训练/微调、多语言检索、实时协同编辑、外部 IM 机器人接入。

### 4.1 Postgres(业务 + 观测)

```

kb_user(id, tenant_id, username, role, ...)            -- role 见 Q-1
kb_base(id, tenant_id, name, embedding_model, chunk_policy)
kb_document(id, tenant_id, kb_id, source_uri, mime, sha256,

kb_chunk(id, tenant_id, kb_id, doc_id, chunk_key,          -- chunk_key 见 §5.3 幂等

kb_entity(id, tenant_id, kb_id, entity_key, etype, label, aliases jsonb)
kb_edge(id, tenant_id, kb_id, src_key, dst_key, rtype,

trace_run(id, tenant_id, thread_id, user_id, query, final_status,   -- answered|refused|error|expired
```

表名按域分组:`kb_`(知识库)、`sec_`(安全审计)、`trace_`(观测)、`eval_`(评估)。迁移 `a1b2c3d4e5f6` 承载改名。

**实现期定稿的补充口径**(2026-11-06):
- **没有 message/conversation 表**:本轮只落 `trace_run` + LangGraph 检查点,多轮上下文不做;会话列表/续跑都靠 `thread_id` 与 checkpoint。
- `chunk.captions` 是视觉回填的落点;视觉描述**只进 `indexed_body`,不进 `chunk_key`**,否则同一张图换一次描述就变成新切片。
- 重切是级联的:删 kb_chunk 同时删 `kb_edge`,graph 阶段 prune 孤儿 `ChunkRef`;Milvus 对账读必须用 **Strong 一致性**(默认 Bounded 的秒级延迟会让孤儿判定失真)。
- `trace_run.final_status` 的 `expired` 落点就是本表,且「expired 删检查点、不删 trace 行」——到期与拒答在统计里是两个数。
- 评估集从反馈导入时,用户提交的正确答案进 `eval_case.reference_answer`;`gold_refs` 仍是 chunk_id 集合,两者语义不能混。

约束要点:
- **所有业务表 `tenant_id` NOT NULL**,且必须有 `(tenant_id, …)` 复合索引。
- `eval_set` 冻结:`frozen_at IS NOT NULL` 时通过触发器拒绝写。
- `eval_run` 用 `cursor_case_id` 支持中断续跑(§8.3)。

Milvus 侧存向量与稀疏倒排,Neo4j 侧存图;Postgres 的 `kb_chunk`/`kb_entity`/`kb_edge` 是**权威记录**,两个引擎是索引投影,可重建。这样图谱路故障时可整库重放,不会数据丢失。

### 4.2 Milvus Collection

```
kb_chunk_index_{tenant_id}      -- 方案 A: 按租户分 Collection
或
kb_chunk_index + partition_key(tenant_id)   -- 方案 B: 单 Collection + 分区键
```

**取方案 B**(分区键),避免租户数增长导致 Collection 爆炸;`tenant_id` 设为 partition key,所有查询强制带该表达式(§6.1 防线③)。

字段:

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `pk` | INT64 | 主键;`auto_id=False`,值由 `chunk_id` 稳定哈希派生(幂等 upsert 的前提) |
| `chunk_id` | VARCHAR | 稳定主键,去重依据 |
| `tenant_id` | VARCHAR, partition key | 隔离键 |
| `kb_id`, `doc_id` | VARCHAR + inverted index | 过滤 |
| `dense` | FLOAT_VECTOR(dim=模型维度) | 语义路,索引 HNSW/COSINE(实测可用) |
| `sparse_body` | SPARSE_FLOAT_VECTOR | 正文 BM25 |
| `sparse_heading` | SPARSE_FLOAT_VECTOR | 章节标题 BM25(**独立一路**) |
| `body_text` | VARCHAR, analyzer `chinese` | BM25 全文输入 → `sparse_body` 由 Function 自动生成 |
| `heading_text` | VARCHAR, analyzer `chinese` | BM25 全文输入 → `sparse_heading` |

**硬约束与坑**(2026-11-05 在 Milvus 2.5.10 上实测,探针 `scripts/verify_milvus.py` 10/10):
1. 一个 Collection 里两个独立 BM25 Function 分别绑定不同输出字段,不能把正文与标题拼成一个字段——拼了就退化成一路,FR-202 的「章节级检索」失效。
2. **`BM25` Function 的输出字段只能建 `metric_type=BM25` 的稀疏索引**;写 `IP` 会被服务端在 `create_index` 阶段直接拒绝(`code=65535, index metric type of BM25 function output field must be BM25, got IP`)。`IP` 那条路只属于外接稀疏向量(如 BGE-M3 自己算好塞进来),本方案没有这种字段,两路稀疏一律 BM25。
3. 中文分词必须显式配 analyzer,默认 analyzer 不分中文词,BM25 会退化成字符级噪声。实测 `analyzer_params={"type": "chinese"}` 下,词 `隔离设计` 只命中含该词的正文行,不会因逐字切分而全命中。
4. 三路混合检索**必须走 `hybrid_search(reqs=[AnnSearchRequest, …], ranker=RRFRanker(k))`**;`search()` 的 `anns_field` 传列表会被客户端拒掉(`ParamError: anns_field value [...] is illegal`)。租户表达式写在每个 `AnnSearchRequest.expr` 里而不是顶层参数,这样三路都自带过滤,不给调用方漏一路的机会。
5. `auto_id=False` 时 `pk` 必须显式给值,否则 insert 报缺主键;`pk` 由 `chunk_id` 的稳定哈希派生,保证重跑落到同一行(upsert 幂等实测 3→3)。
6. **对账读必须用 Strong 一致性**:默认 Bounded 的秒级延迟会让刚删/刚写的行在核对时不可见,孤儿判定与计数都会失真。视觉回填的 caption 只进 `indexed_body`,不进 `chunk_key` —— 同一张图换描述不应产生新切片。

### 4.3 Neo4j

```
(:Entity {tenant_id, kb_id, entity_key, etype, label})
(:ChunkRef {tenant_id, chunk_id, doc_id})
(:Document {tenant_id, doc_id, title})

约束(实测可用):
CREATE CONSTRAINT entity_tk_unique IF NOT EXISTS
  FOR (e:Entity) REQUIRE (e.tenant_id, e.entity_key) IS UNIQUE;
CREATE CONSTRAINT chunkref_tk_unique IF NOT EXISTS
  FOR (c:ChunkRef) REQUIRE (c.tenant_id, c.chunk_id) IS UNIQUE;
CREATE CONSTRAINT document_tk_unique IF NOT EXISTS
  FOR (d:Document) REQUIRE (d.tenant_id, d.doc_id) IS UNIQUE;
CREATE INDEX entity_tenant IF NOT EXISTS FOR (e:Entity) ON (e.tenant_id);

关系:
(:Entity)-[:REL {rtype, evidence, chunk_id}]->(:Entity)     -- 业务关系,方向必须保留
(:Entity)-[:MENTIONED_IN {evidence}]->(:ChunkRef)           -- 桥接关系,回落原文
```

设计决策:
- **实体规范化在前,写图在后**:`entity_key` 由「规范化标签 + 别名表归一」得到,稳定主键是幂等写入与去重的唯一支点。
- **关系类型不参数化**:`rtype` 存为属性,图上一律用 `[:REL]` 承载(变长遍历同理)。取舍见 §6.4——白名单在应用层做,而不是靠 Neo4j 关系类型做。
  - 代价:失去按关系类型建索引的收益 → 用 `CREATE INDEX rel_rtype IF NOT EXISTS FOR ()-[r:REL]-() ON (r.rtype)` 补。
  - 收益:查询可参数化、白名单校验只有一处、Schema 演进不需重建约束。
- 每条 `REL` 必须带 `evidence` + `chunk_id`,否则审计要求(FR-305)不达标,写入层直接拒绝。
- 遍历用**无向** `-[r:REL]-` 保证召回,但返回必须带 `startNode(r)`/`endNode(r)` 还原方向(FR-212)。

**硬约束与坑**(2026-11-05 在 Neo4j 5.26.32 community 上实测,探针 `scripts/verify_neo4j.py` 15/15):
1. 复合唯一约束 `(tenant_id, entity_key)` 可用;`MERGE` 三重放只落一行(幂等第三层成立)。同一 `entity_key` 在不同租户下**允许并存**,所以隔离只能靠 `tenant_id`,不能指望 key 全局唯一。
2. 关系类型写在方括号里(`-[r:$RT]->`)与变长跳数(`*1..$N`)都在**解析期**被拒(`ClientError.Statement.SyntaxError`),即使把参数值传进去也一样。可行的替代是无类型遍历 + `type(r) IN $types` / `r.rtype IN $types`(实测可参数化),跳数由白名单 `{1,2,3}` 渲染成字面量。§6.4 的白名单不是洁癖,是唯一能跑的写法。
3. 无向变长遍历返回的每条边仍带真实端点(`startNode(e)/endNode(e)`),子图线性化不会把 `A→B` 渲染成 `B→A`(实测边集方向正确)。
4. **只在起点绑 `tenant_id` 会串数据**:一条漏写 `tenant_id` 的边(管道 bug)就能让 3 跳遍历爬进别租户并把它返回出来。防线是逐跳过滤 `all(e IN relationships(p) WHERE e.tenant_id = $t)`,实测加上后跨租户命中归零。仓库层不得只写 `(a {tenant_id: $t})`。
5. **社区版没有可配置的分析器**:`index.search.analyzer` / `analyzer` / `index.analyzer` 一律 `Invalid index config key`(自定义分词是企业版特性)。默认分析器对中文按**单字 + AND** 匹配,所以乱序两字(`型奖`)也会命中 `奖励模型` —— 全文索引只能当**候选生成器**,实体链接第②级的判定必须自己做归一化 + 编辑距离,并对候选规模设上限。
6. **全文索引是全局的、不认识租户**:`db.index.fulltext.queryNodes` 会返回别租户的实体,命中集必须在服务端按 `tenant_id` 再收口(防线③在图谱路的等价形式)。
7. **`REQUIRE ... IS NOT NULL` 是的企业版特性**:社区版建它直接 `ConstraintCreationFailed: Property existence constraint requires Neo4j Enterprise Edition`。所以「节点必须带 tenant_id」只能在**写入层**拦(§5.1 `write_graph` 落图前校验),图上只留唯一约束 + `tenant_id` 普通索引;漏写属性的边靠第 4 条的逐跳谓词兜住,不靠约束。
8. **实体唯一键不能带 `kb_id`**:Postgres `kb_entity` 的唯一约束是 `(tenant_id, entity_key)`,图上若多绑一个 `kb_id`,同一实体跨库就会出现「PG 一行、图里两节点」的分叉,重索引永远收不拢。两库同源,键必须一致(实测:三次 `MERGE` 只落一行)。

## 5. 离线索引管道(Celery)

### 5.1 任务 DAG

```
parse_document(doc_id)
  ├─ extract_text / pdfplumber / ocr
  ├─ split_chunks(doc_id, policy)        → 写 Postgres chunk(幂等)
  ├─ caption_images(doc_id, pages)       → 回填 chunk.image_refs/text
  ├─ embed_chunks(batch)                 → 写 Milvus dense+sparse(幂等 upsert)
  ├─ extract_triplets(doc_id)            → Schema 约束抽取,过白名单校验(第1道)
  ├─ write_graph(doc_id)                 → MERGE 写入,再校验一次(第2道)
  └─ link_chunks_to_entities(doc_id)     → MENTIONED_IN 桥接
```

### 5.2 状态机与可观测

`document.parse_status`:`PENDING → PARSING → CHUNKED → EMBEDDED → GRAPH_QUEUED → GRAPH_DONE → DONE`,失败进 `FAILED(stage, error, retry_count)`。每个跃迁更新 `trace`/Celery 任务元数据,前端可轮询进度(FR-106)。跃迁只允许前进或回到同 stage 重试,禁止跳跃——保证重跑可判定。

实现期补充(2026-11-06):除了向前/原地重试,状态机还允许两类合法转移 —— **原地重跑退一格**(阶段失败后从同阶段前一步重来)与 **DONE→head 重索引**(`index_version` 递增,回到 `PENDING` 开新一轮)。后者不是跳跃:任务幂等靠 `index_version` 隔离,不靠状态机拦。

### 5.3 幂等的三个层次

| 层次 | 幂等键 | 实现 |
| --- | --- | --- |
| 切片 | `chunk_key = sha256(doc_id + heading_path + norm_text)` | `INSERT … ON CONFLICT (tenant_id, chunk_key) DO NOTHING` |
| 向量 | `chunk_id` 作 Milvus 侧映射,先 upsert 后按 `chunk_id` 删旧 | Milvus upsert 语义 + 收尾删除「本批次不在集合中的孤儿 pk」 |
| 图谱 | `(tenant_id, kb_id, entity_key)` MERGE | `MERGE` + 关系 `ON CREATE/ON MATCH` 都覆盖 `evidence` |
| 任务 | Celery `task_id = f"{doc_id}:{index_version}:{stage}"` + Redis SETNX 幂等锁 | 同一 index_version 重复投递直接短路返回已有结果 |

`index_version` 在解析策略或嵌入模型变更时递增——这是「重索引」与「上线新版本」的统一入口,不需要专门的迁移脚本。

### 5.4 锁不得跨外部 I/O(重点陷阱)

规则:**持锁区间内不允许任何网络调用**(LLM、Milvus、Neo4j、HTTP)。

```python
# 反例(常见事故):事务/Redis 锁里跑模型
with db_txn(), tenant_lock(tenant_id):     # 锁内调 LLM → 连接池耗尽、锁等待雪崩
    triples = llm.extract(text)
    neo4j.write(triples)

# 正解:三段式
lease = acquire_lease(key, ttl=30)         # 1) 短临界区:抢占标记
triples = llm.extract(text)                # 2) 无锁:长耗时外部 I/O
with db_txn():                              # 3) 短临界区:写入 + 校验
    validate(triples); graph.merge(triples)
release_lease(lease)
```

补充:`llm.extract` 超时/异常必须让 lease 靠 TTL 自然过期,不能吞掉异常后直接 release(会让下一个 worker 看到「已成功」的假状态)。

## 6. 检索实现

### 6.1 四道防线在代码里的落点

| 防线 | 落点 |
| --- | --- |
| ① 存储层物理隔离 | Milvus partition key;Neo4j 复合唯一约束含 `tenant_id`;PG 全部表 `tenant_id NOT NULL` + 复合索引(可选 RLS 加固) |
| ② 身份层 | `get_tenant_context(authorization: str) -> TenantContext` 为 **FastAPI 依赖**,只从验签后的 JWT claims 取 `tenant_id` |
| ③ 查询层 | 仓储层函数签名**不接收** `tenant_id` 参数,只接收 `TenantContext`;任何检索请求在门面里强制 `expr = f"tenant_id == '{ctx.tenant_id}'"` 再拼接业务过滤 |
| ④ 验收层 | `tests/test_tenant_isolation_e2e.py` 用真实多租户数据跑越权用例(见 §9) |

防越权的类型层做法(不是「前端藏按钮」):

```python
@dataclass(frozen=True)
class TenantContext:
    tenant_id: str
    role: Role
    kb_scope: frozenset[str]

class ChunkRepo:
    def __init__(self, ctx: TenantContext, milvus: MilvusClient): ...
    def search(self, q: Query) -> list[Hit]: ...   # 无 tenant_id 形参 → 调用方无从传入他租户
```

任何函数签名里出现裸 `tenant_id: str` 参数都视为缺陷,代码审查拦住。

### 6.2 三路召回 + RRF

```
Route-1 sparse_body      正文 BM25        top_k=50
Route-2 sparse_heading   章节标题 BM25    top_k=50
Route-3 dense            语义 ANN(HNSW)  top_k=50
(可选) Route-4 graph     图谱路           top_k=30
```

RRF:`score(d) = Σ_r weight_r / (k + rank_r(d))`,`k=60`(业界默认,先不玄学调参)。三路默认等权;RRF 输出 top 30 → cross-encoder 精排 → top 8 进上下文。

**每路独立可验证**(FR-205)是工程要求不是洁癖:
- 检索门面每次调用记录 `route_stats = {route: {候选数, 命中 chunk 集合 hash}}`;
- 评估运行器支持 `routes=["body"]` 单路模式跑同一评估集,得到每路独立指标;
- 任一路在真实语料上长期命中率为 0 → 在线告警。**这是发现「标题路配了但分词没生效、被正文路掩盖」这类静默失效的唯一手段。**

### 6.3 图谱路五步

```
① 实体抽取   query → 候选 mention(结构化输出,禁自由文本)
② 实体链接   L1 严格匹配 entity_key/alias → L2 字符匹配(normalize + 编辑距离阈值 0.8)
             两级都留候选与置信度;L2 命中数 > 阈值视为低置信,图谱路降级为不启用
             全文索引只做**候选生成**:社区版没有自定义分词、默认按单字 AND,且命中不认租户,
             判定与收口都在应用层(§4.3 坑 5、6)
③ 邻域扩展   受控跳数 n ≤ [待确认 Q-5](默认 2),用变长路径 *1..n
             —— 变长不可参数化 → n 从白名单 {1,2,3} 取,禁止字符串插值任意整数
             —— 谓词必须逐跳生效:all(e IN relationships(p) WHERE e.tenant_id = $t);
                只在起点绑租户挡不住漏写属性的边(§4.3 坑 4)
④ 子图线性化 每条边渲染为 "srcLabel --rtype--> dstLabel  (依据: evidence 摘要)"
             保留方向;按边相关性排序后截断(默认 ≤ 30 条边)
⑤ 回落切片   子图节点 → MENTIONED_IN → chunk_id 集合,交回统一 Hit 契约
```

统一 Hit 契约(双库融合的前提,§6.4):

```python
@dataclass
class Hit:
    chunk_id: str          # 去重键 —— 稳定主键,不用文本 hash 去重
    score: float           # 精排后统一分,路内分不跨路比较
    source_routes: set[str]
    citation: Citation     # doc_id/page/heading_path
    evidence: str | None   # 图谱路必须回填原文依据
```

两路结果只在 `Hit` 层合并,合并即去重(`chunk_id` 并集)、统一精排,保证「图谱命中」永远有原文可引(FR-209)。

### 6.4 注入防护(图查询)

- 关系类型、跳数:白名单枚举,**永不参数化进 Cypher 字符串**。
- 实体 label 等值匹配:走参数 `$label`,并用 `entity_key` 而非自由文本匹配。
- 单测里放一条 `'MATCH (n) DETACH DELETE n'` 形态的恶意输入,断言被白名单拒绝——把「不可参数化」的绕法变成可执行测试,不靠人记住。

## 7. 在线问答编排(LangGraph)

### 7.1 状态图

```
START → route_intent → rewrite_query → confirm_interrupt → retrieve_dual
      → dedupe → rerank_fused → assess_relevance ─┬→ retry_targeted ─┐(回 retrieve_dual,≤2 次)
                                                  ├→ refuse ─────────┐
                                                  └→ generate_cite → END
```

State 字段:`query, intent, rewrite_candidates, user_choice, route_flags, hits, reranked, relevance_scores, missing_info, answer, citations, final_status`。

实现期新增(每条都已在代码 `agents/state.py` 登记):`thread_key / run_id / config_hash`(身份与配置指纹)、`confirmed_query`(检索用确认后的词)、`queries_tried / retry_constraints / retry_attempt / seen_chunk_ids / evidence_gain`(FR-405「禁止原样重跑」的判据与预算)、`cite_ids`(编号→chunk_id 的冻结映射,层 5 唯一真源)、`reject_code`(与 `final_status` 双字段,满足 FR-406 数据层可分)、`pending_since`(TTL 判据随检查点落盘)、`degraded / dropped / route_stats / graph_trace / trace_seq / usage / error`。

节点契约:
- `route_intent` / `rewrite_query` / `assess_relevance` / `extract_entities` 四类**必须用结构化输出**(Pydantic schema + 严格 JSON),不允许「模型自己写一段话再解析」。
- 思考模式与工具调用冲突:需要工具的场景不叠加 `thinking`/`reasoning` 开关;需要严格 schema 的场景关掉思考模式再调 —— 这条要在 LLM 网关的调用参数封装里固化,不能每个节点自己拼(FR-407)。

### 7.2 中断与恢复

实现期定稿为**全异步图 + `AsyncPostgresSaver`**(2026-11-06 用户拍板,覆盖原同步片段):

```python
saver = AsyncPostgresSaver(pool, serde=…)        # pool options="-c search_path=lg"
graph = build_graph(deps).compile(checkpointer=saver)
cfg = {"configurable": {"thread_id": f"{ctx.tenant_id}:{thread_id}"}}
await graph.ainvoke(input, cfg)                  # 走到 confirm_interrupt 自动 interrupt()
# 用户选择候选改写后:
await graph.ainvoke(Command(resume={"choice": 2, "edited": "..."}), cfg)
```

要点:
- `thread_id` **前缀租户 ID**,跨租户恢复在同一实例上物理不可能;恢复请求仍走 §6.1 的 `TenantContext` 依赖。
- 检查点在 PG 的 `lg` schema,服务重启后 `thread_id` 可继续 —— 验收用两个真实子进程 + SIGTERM 跑通(见 §9)。
- 中断超时策略:`PENDING_CONFIRM_TTL`(默认 30 min)后视为放弃,状态转 `expired` 并删检查点,不永久占用会话。
- **非法 `Command(resume)` 会毒化线程**(实测):坏值一旦写进 checkpoint,之后每次 resume 都重放它;因此 `Runtime.resume` 在碰图之前用纯函数 `guards.validate_resume` 预检,非法确认返回 409 且同一线程仍可再次确认。节点内校验保留作纵深防御。
- **检查点持久化不可关闭的可测依据**不是 `interrupt()` 抛错(无 checkpointer 时 runner 会静默吞掉中断),而是 `aget_state` 抛 `ValueError("No checkpointer set")`;编排层拿到非终态时一律落 `error`。
- `resume` 的幂等口径:`snap.next == ()` 直接回放既有答案,不重跑;`snap.next != ("confirm_interrupt",)` 抛 `IllegalTransition`。

### 7.3 五层幻觉防御(逐层实现)

| # | 层 | 实现 | 失败动作 |
| --- | --- | --- | --- |
| 1 | 意图路由过滤 | `route_intent` 判 可答/闲聊/越权/超范围 | 越权与超范围直接终态,不进检索 |
| 2 | 相关性评估打分 | 每条 reranked hit 打 0~1 分 | 低于 `θ_rel=0.35` 丢弃 |
| 3 | 定向重试 | 汇总 `missing_info`(缺哪一类事实/哪个时间段),据此改写重检 | 最多 2 次,每次重检必须带新增约束,禁止原样重跑(FR-405) |
| 4 | 明确拒答 | 有效证据数 < 1 或最高分 < `θ_answer=0.45` | `final_status="refused"`,答案模板固定「证据不足」,不生成自由解释 |
| 5 | 引用编号硬校验 | 生成带 `[n]` 后,程序侧解析 n 并核对 `n ≤ len(citations)` 且该 citation 真在证据集内 | 越界编号剥离并记录;不可解析则整条答案走 refuse 分支 |

第 5 层必须在服务端:模型自证「我有引用」不算校验。

实现期定死的 `[n]` 契约四条:
1. 编号 **1-based**;全角方括号 `【1】`、全角数字 `［１］`、`[1,2]` 都按引用解析。
2. 只有「方括号内全部是数字」才是引用候选;`[图1]`、`[详见第3章]`、markdown 链接不算,不剥离也不因此拒答。
3. 越界/映射缺失/映射到的 chunk 不在证据集内 → 从正文**剥离并记录**,不重编号、不改写其余正文。
4. 零个可解析 `[n]`,或剥离后归零 → `cite_unparsable`,整条走 refuse。`citations` 在生成**之前**按精排顺序冻结,`cite_ids` 是唯一真源。

### 7.4 流式输出

SSE 事件:`route` / `rewrite_candidates` / `retrieval_done` / `token` / `citations` / `done` / `error`,中断时下发 `await_confirm`,另加 `degraded`(#7 实现为九类)。可观测 Callback 与 SSE 分通道,观测侧故障不阻断问答(与项目十二同构的三通道解耦思路)。

实现口径(2026-11-06):SSE 响应按规范用 **CRLF** 分帧,测试/排障的 `parse_sse` 必须先归一化行尾;图执行在 producer 任务里,HTTP 消费端只读无界队列,客户端慢/断不会阻塞留痕提交。`done` 帧里的 citations 与 `citations` 帧同为原生 dict,不得把 `Citation` dataclass 直接 JSON 化。

## 8. 评估与反馈

### 8.1 四层指标与计算口径

| 层 | 指标 | 口径(唯一算法,不允许多义) |
| --- | --- | --- |
| 检索层 | `recall@k` / `mrr` / `ndcg@10` | gold = `eval_case.gold_refs` 的 chunk_id 集合;k 取精排后进入上下文的 top-N |
| 答案层 | `faithfulness` / `answer_relevancy` / `citation_validity` | faithfulness = 断言中被证据支持的比例(LLM judge,双次采样一致才计入);citation_validity = 程序侧可解析且指向真证据的编号占比 |
| Agent 层 | `rewrite_accept_rate` / `retry_success_rate` / `refuse_correctness` | 拒答正确性 = 应拒答集(无证据构造)中被拒的比例 |
| 系统层 | `p50/p95 latency` / `token` / `cost` / `error_rate` / `route_degraded_rate` | 按 trace_run 聚合,阶段耗时取 trace_step |

### 8.2 分组切片统计

`eval_case.group_key` ∈ `{multi_hop, relational, aggregation, factual_single, keyword_exact, image_derived, out_of_scope}`。报告按 group 出四层指标,并与基线逐 group 相减 —— 总分不降但 `multi_hop` 变差的改动必须拦住(FR-604)。

### 8.3 在线 + 离线双闭环

- **在线**:每次问答结束后异步投递评估任务(不进主链路)。格式/引用/安全为全量规则检查;忠实性与相关性按 `online_eval_sample_rate`(默认 10%)抽样 `[待确认 Q-4 阈值]`。
- **离线**:`eval_set` 从 `kb_feedback` 导入(用户评分 + 提交的正确答案 → 反馈池 → 候选 case → 人工确认 → 冻结版本)。评估运行器:
  - 逐 case 落 `eval_result`,写 `cursor_case_id`,**可中断可续跑**;
  - 一次运行可绑多组 `config_snapshot`(routes 开关、k、θ、rerank 模型版本)做对照;
  - 输出回退样本明细(`group_key`、query、基线答案、本次答案、指标差值)+ CSV 导出。

### 8.4 发布门禁

基线回归对比:任一分组指标劣化超过 `regression_gate`(默认 -2pp)`[待确认 Q-4]` → 阻断上线,列出回退样本。配置指纹(`config_snapshot`)进 `eval_run`,让「一次改动 vs 收益」可归因。

### 8.5 实现落地(2026-11-06)

- 指标口径落在 `eval/metrics.py`,全部纯函数:`recall@k` / `mrr` / `ndcg@10`;`citation_validity` 按**编号**计(不是去重 chunk 数);Agent 层三个比率的适用样本分别排除「无候选 / 无重试 / 不应拒答」;系统层 p50/p95 线性插值。
- 离线运行器 `eval/runner.py`:`answer_case` 注入,生产桥接是 `eval/runtime_case.py`(同一套 Runtime/五层防御,自动选第一条改写候选);每完成一个 case 提交 `cursor_case_id`,失败可续跑;`report()` 按 group 输出四层指标,`compare()` 输出 group×metric 差值,`regression_csv()` 导出回退样本明细。
- 在线评估 `eval/online.py` + `eval/tasks.py`:格式/引用/安全全量规则检查;faithfulness/answer_relevancy 按 `online_eval_sample_rate` 抽样,双次采样差 >0.1 视为不一致、该样本不计入。结果落 `platform.eval_online`(一次 run 一行),失败样本通过 `GET /api/online-evals/failures` 查询;问答收尾只在 `answered/refused` 时异步入队,不阻断主链路。
- 评估端点:`POST /api/eval-runs/{id}/execute`(投 worker)、`GET …/report`、`GET …/regressions?baseline_run_id=`、`GET …/export.csv?baseline_run_id=`;反馈导入 `POST /api/eval-sets/from-feedback`。评估集创建/导入/冻结/建 run 均需 tenant_admin+ 角色。
- 评估执行本身用 Celery(`kbmesh.eval.run`),执行完写 `eval_result` 并收尾 `eval_run`;HTTP 只负责排队与查报告。
- 管理端点(2026-11-19 补齐):KB CRUD `POST/GET/DELETE /api/kbs`(写操作 tenant_admin+);租户 CRUD `/api/admin/tenants`(platform_admin);用户 CRUD `/api/admin/users`(tenant_admin+)。
- 拓扑可视化:`GET /api/graph/topology` 返回 mermaid 文本与节点列表(FR-401)。
- 路命中告警:`GET /api/traces/stats` 返回 `route_alerts` 字段,窗口内命中归零的路列入告警(FR-205)。

## 10. 可降级开关矩阵

| 组件 | 性质 | 开关 | 故障/关闭时行为 |
| --- | --- | --- | --- |
| 意图路由 | 必需 | 无 | 不可降级(越权拦截依赖它) |
| 正文 BM25 | 必需 | 无 | 不可降级 |
| 章节标题 BM25 | 增益 | `route_heading` | 退化为两路 |
| 语义向量 | 必需(默认) | — | 若 embedding 服务故障 → 关键词路 + 明确 degraded |
| 图谱路 | 增益 | `route_graph` | 纯向量+关键词,`multi_hop` 指标预期下降需在报告标注 |
| 交叉精排 | 增益 | `enable_rerank` | 按 RRF 原序截断 |
| 相关性交叉验证 | 增益 | `enable_crosscheck` | 保留打分与拒答,关闭二次验证 |
| 在线评估 | 增益(异步) | `online_eval_enabled` | 关闭不影响问答 |
| 检查点持久化 | 必需 | 无 | 不可降级(人机协同依赖) |

原则:降级路径不改变答案的正确性标准,只改变召回能力;宁可 degraded 也不静默降质。

实现期补充(2026-11-06):
- **改写节点故障**不在原矩阵:模型挂 → `rewrite_candidates=[]`,确认框只接受 `edited`,并记 `degraded`;不静默回退原问(否则等于跳过确认)。

## 11. 可观测与成本

`trace_step.stage`:`route_intent / rewrite / retrieve_body / retrieve_heading / retrieve_dense / retrieve_graph / merge / rerank / assess / retry / generate / cite_check`。

每步记录:候选数、分数向量摘要、耗时、token_in/out、模型版本、`config_snapshot` hash。聚合视图按租户出:量、P95、token、成本、拒答率、降级率、路命中分布。成本口径:`cost = token_in×单价_in + token_out×单价_out + rerank次数×单价`,单价表版本化(换模型时历史成本不失真)。

实现落地(2026-11-06):
- 单价表在 `observability/pricing.py`,`PRICE_TABLE_VERSION` 随每次算成本写进 `trace_run.config_snapshot`;未登记模型按 0 计而不抛错(缺价由版本号与 0 成本暴露,不把问答打成 500)。运营单价未确认前默认全 0。
- 聚合在 `observability/aggregate.py`(纯函数):`runs / answered / refused / error / expired / refusal_rate / error_rate / degraded_rate / latency_ms{p50,p95} / token_in / token_out / cost_usd / route_hits / stage_latency_ms / tokens_by_stage / tokens_by_model`。后两项满足 FR-703「按阶段与按模型汇总」。
- 查询端点:`GET /api/traces/stats?limit=` 按当前租户返回上述聚合;`GET /api/traces/runs/{id}/online-eval`、`GET /api/online-evals/failures` 查在线评估。
- `trace_step` 的 `payload` 记录候选数/名次摘要,`latency_ms/token_in/token_out/model` 是列,不塞进 JSON;rerank 次数按 `stage="rerank"` 且 `payload.enabled=true` 计。

## 12. 部署

- 容器化:`api` / `worker` / `beat` / `web-admin` / `web-chat`;依赖 PG、Redis、MinIO、Milvus、Neo4j。
- 中间件复用:PG/Redis/MinIO 可直接连部署环境提供的基础设施(见全局约定);Milvus、Neo4j 待确认(§3)。
- Worker 并发:`prefork`,数量按 CPU 而非模型 QPS;**LLM 调用走独立小并发 + 令牌桶**,防止 worker 数放大打爆模型配额。
- 密钥:`.env` 注入,不进仓库。
- 对象存储:MinIO 上建专用桶 `kbmesh-artifact`;应用侧凭据只在 `.env`,不写进仓库或 `deploy/` 以外的配置。
- 上线顺序:先建 Milvus Collection(分区键 + 双 BM25 Function + analyzer)与 Neo4j 约束 → 再放 worker 跑存量文档 → 最后开在线评估抽样,避免抽样评估在索引未就绪时产出无效基线。
